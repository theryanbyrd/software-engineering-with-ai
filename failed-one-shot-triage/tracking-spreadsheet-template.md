# Tracking Spreadsheet Template

The shared spreadsheet structure. Per Ch 31 §31.5: "do not bother building elaborate tooling for it; a shared spreadsheet works."

## Why a spreadsheet

The discipline is in the triage itself, not the surface area of the tracking. A spreadsheet:
- Is universally accessible (every team has one)
- Doesn't require platform team time to maintain
- Doesn't have its own bug surface
- Easy to adapt as the team's needs evolve

Don't gold-plate. A simple shared sheet beats a custom tool for this discipline.

## Recommended structure

### Tab 1 — Failures (the weekly log)

Columns:

| Column | Description |
|---|---|
| **Date** | When the failure occurred |
| **Engineer** | Who ran the agent (for follow-up only; not for surveillance) |
| **Spec / ticket** | Link to the ticket the agent was working on |
| **Tier** | T1 / T2 / T3 (per Ch 19 §19.5) |
| **Model** | Haiku / Sonnet / Opus / other |
| **Approximate cost** | From the gateway data; rough is fine |
| **What happened** | 1-2 sentences describing the failure |
| **Initial classification** | Engineer's first guess: Score / Question / Opportunity / Train |
| **Final classification** | Confirmed at retro |
| **Resolution** | What was done about it (open ticket link, coaching note, etc.) |
| **Owner** | Person responsible for the resolution |
| **Status** | Open / In progress / Closed |

### Tab 2 — Successes (the Score log)

Columns:

| Column | Description |
|---|---|
| **Date** | When the work was done |
| **Engineer** | Who ran the agent |
| **Spec / ticket** | Link |
| **Tier** | T1 / T2 / T3 |
| **Model** | Which model |
| **Approximate cost** | Rough |
| **Time** | From spec to merged PR |
| **Notes** | Anything worth remembering |

The Score log is lighter — most successes don't warrant detailed notes. The patterns matter more than the individual entries.

### Tab 3 — Trends

A summary view that updates weekly:

| Week | Total invocations | Score | Question | Opportunity | Train | Score % |
|---|---|---|---|---|---|---|
| 2026-W18 | 47 | 39 | 1 | 4 | 3 | 83% |
| 2026-W19 | 52 | 44 | 0 | 5 | 3 | 85% |
| ... | | | | | | |

Roll up monthly and quarterly. The trend is the harness-maturity signal.

### Tab 4 — Open Opportunities

Tracks the harness improvement backlog generated by Opportunity classifications:

| Opened | What's missing | Where it should live | Owner | Status |
|---|---|---|---|---|
| 2026-04-22 | Missing fixture for billing tests | `tests/billing/fixtures/` | @platform-team | Open |
| 2026-04-29 | AGENTS.md for auth module | `services/auth/AGENTS.md` | @auth-team | In progress |
| 2026-05-04 | Skill missing for log analysis pattern | `.claude/skills/log-analysis/` | @platform-team | Open |

Reviewed weekly at retro.

### Tab 5 — Question log

Tracks capability gaps for next model review:

| Date | Work type | What the model failed at | Models tried | Status |
|---|---|---|---|---|
| 2026-04-15 | Multi-step reconciliation logic | Lost track of state across 4+ steps | Sonnet 4.6, Opus 4.7 | Open; revisit on Sonnet 5 |
| 2026-04-22 | TypeScript type inference for complex generics | Couldn't infer the right type bounds | Sonnet 4.6 | Open |

Reviewed quarterly during the model lineup review (per `evals-and-benchmarks-runbook/quarterly-model-lineup-review.md`).

## Setup

A typical setup time is 15-30 minutes:
1. Create a shared Google Sheet / Excel / Airtable
2. Create the four tabs
3. Add column headers per the templates above
4. Share read-write access to the team
5. Add a link to the team's CLAUDE.md / AGENTS.md / wiki

That's the whole infrastructure. Per Ch 31 §31.5: "Do not bother building elaborate tooling."

## Logging discipline

For the spreadsheet to be useful, engineers need to log consistently:

### What's logged

- **Every failure** that doesn't merge on first run
- **Every meaningful success** (the Score log; not necessarily every PR)

### What's NOT logged

- Tooling errors (gateway down, network issue) — those are platform issues
- Engineer-side errors (typo'd command, wrong directory) — not relevant to harness/spec quality
- Trivial typo fixes that succeed routinely (Score logging here adds noise without signal)

### When to log

Within 24 hours of the failure (or success). Logging at the end of the week loses detail. Logging in real time loses focus.

A common pattern: end-of-day, log any failures from the day in 5-10 minutes.

### How much detail

Minimum viable. The "what happened" field is 1-2 sentences. Don't write paragraphs; the retro discussion adds detail.

## Privacy

For Train classifications specifically, consider the privacy implications:

- The Train coaching is private (1:1 with manager). The spreadsheet entry exists; the coaching doesn't appear there.
- Some teams anonymize Train classifications in the spreadsheet (no engineer name; just "Train"). Trade-off: harder to surface patterns; less surveillance.
- The "engineer" column should never feed performance reviews. If it does, engineers stop logging honestly.

## Maintenance

### Weekly

The triager (or facilitator):
- Reviews the week's logged failures before retro
- Drafts classifications
- Spots patterns

### Monthly

Roll up the data:
- Update Tab 3 (Trends)
- Review patterns over the month
- Identify any structural issues

### Quarterly

- Review Question log against the model lineup review (per `evals-and-benchmarks-runbook/`)
- Review whether the spreadsheet structure is still serving the team
- Adjust columns / tabs if needed

## When to migrate to a tool

Some teams outgrow the spreadsheet. Triggers:

- **Volume**: 100+ failures per week makes the sheet unwieldy
- **Multi-team**: aggregating across many teams becomes painful
- **Reporting**: leadership needs structured rollups beyond what the sheet provides

When this happens, consider:
- A simple internal tool that replaces the sheet
- An off-the-shelf incident/issue tracker repurposed
- Adopting a metrics platform that already does aggregation

The migration cost is real. Most teams don't outgrow the spreadsheet. Per Ch 31 §31.5: don't build before you need to.

## Anti-patterns

### Spreadsheet drift

The spreadsheet exists but stops being maintained. Entries are stale; classifications are absent.

Mitigation: weekly retro discipline. The spreadsheet is the agenda for the triage section.

### Spreadsheet bureaucracy

The team adds 20 columns. Each entry takes 5 minutes to log. Engineers stop logging.

Mitigation: minimum viable. The recommended columns are sufficient. Resist additions.

### Spreadsheet without trend

Tab 1 grows but Tab 3 (Trends) is never updated. The cumulative signal is lost.

Mitigation: monthly rollup is the discipline. Even 5 minutes to update the trend tab is enough.

### Per-engineer spreadsheets

Each engineer has their own spreadsheet "for personal tracking." Team-level patterns can't be seen.

Mitigation: one shared spreadsheet for the team. Per-engineer notes can be private; the team data is shared.
