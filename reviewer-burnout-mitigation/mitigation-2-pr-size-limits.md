# Mitigation 2 — Hard PR Size Limits

The discipline of decomposition. Per Ch 44 §44.5:

> Hard PR-size limits. Diffs over 400 lines are auto-flagged for split. Most agent-generated diffs do not need to be 800 lines; they are because the engineer didn't decompose. Enforce decomposition.

## Why size limits

Larger PRs:
- Take longer to review (non-linear; a 800-line PR takes more than 2× the time of a 400-line PR)
- Catch fewer issues (reviewer fatigue accumulates within a single PR)
- Bundle unrelated changes (scope creep)
- Are harder to revert (more potential collateral damage)
- Block more downstream work (the queue grows)

The empirical observation: teams that enforce size limits have lower review queue depth, faster median time-to-merge, and fewer reverts. Per Ch 44 §44.5, "most agent-generated diffs do not need to be 800 lines; they are because the engineer didn't decompose."

## The threshold

Ch 44 §44.5 specifies 400 lines. This is the recommended starting point.

Adjust based on team context:
- **400 lines (default)**: most teams' sweet spot
- **300 lines**: tight discipline; works well for high-quality codebases
- **500 lines**: looser discipline; appropriate for exploratory work or specific contexts
- **600+ lines**: probably too loose; the cognitive cost of review is too high

For teams just starting: begin at 400; adjust based on data.

## What counts as "lines"

Specific definition matters:

- **Net lines added + lines removed**: typical metric
- **Excludes**: generated files (lockfiles, autogenerated code), pure renames, pure formatting changes
- **Includes**: code changes, tests, documentation prose changes

A PR with 200 lines of code change and 200 lines of tests is 400 lines. A PR with 200 lines of code and 600 lines of generated lockfile changes is effectively 200 lines.

The tooling needs to make this distinction. Most CI integrations can be configured to.

## Auto-flag, not auto-block

The book says "auto-flag for split," not "auto-block." The distinction matters.

**Auto-flag**: the PR can still be opened, merged with effort, but the size is surfaced. Reviewers see "this PR exceeds the size limit" prominently.

**Auto-block**: the PR can't merge until decomposed. Stronger, but produces friction.

Recommended: auto-flag with social pressure to split. Auto-block reserves for specific paths (e.g., security-sensitive code where large changes are inherently more dangerous).

The flag mechanism:
- Bot comment on the PR: "This PR is 547 lines. Consider splitting."
- Label: `large-pr` or similar
- Reviewer sees it in the GitHub UI before reviewing

## Implementing the limit

### CI check

A simple CI step counts the diff size and posts a comment / sets a label if over threshold:

```yaml
# .github/workflows/pr-size-check.yml
name: PR Size Check
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  size-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: |
          # Compute diff size excluding generated files
          ADDITIONS=$(git diff --numstat origin/main HEAD -- ':!*.lock' ':!**/generated/**' | awk '{sum += $1} END {print sum}')
          DELETIONS=$(git diff --numstat origin/main HEAD -- ':!*.lock' ':!**/generated/**' | awk '{sum += $2} END {print sum}')
          TOTAL=$((ADDITIONS + DELETIONS))
          if [ $TOTAL -gt 400 ]; then
            gh pr comment ${{ github.event.pull_request.number }} --body "⚠️ PR size: $TOTAL lines (exceeds 400). Consider splitting."
            gh pr edit ${{ github.event.pull_request.number }} --add-label "large-pr"
          fi
```

This is the minimum viable. Teams typically iterate to handle edge cases (specific paths, exceptions for migrations, etc.).

### CODEOWNERS escalation

For specific paths, larger PRs may require additional reviewer approval:

```
# CODEOWNERS
# Auth code changes >200 lines require security team review
/services/auth/ @security-team
```

This is a different mechanism than size limit — the size limit is the team norm; CODEOWNERS is path-specific.

### Bypass mechanism

Sometimes large PRs are necessary:
- Initial scaffolding for a new service
- A generator-driven change (refactor that touches many files mechanically)
- A migration that's atomic by nature

The bypass:
- Engineer adds a label: `large-pr-justified`
- Justification in the PR description: why this can't be split
- The flag appears but doesn't gate

Don't make bypass painful — but make it deliberate. If engineers bypass routinely, the limit isn't working.

## When agents produce large PRs

Per Ch 44 §44.5: "Most agent-generated diffs do not need to be 800 lines; they are because the engineer didn't decompose."

The pattern:
- Engineer writes a single agent-ready issue covering substantial scope
- Agent implements the whole thing in one PR
- PR is 700-900 lines

The fix: decomposition before the agent runs. The engineer breaks the work into 2-3 issues; agent works on each separately.

This is a coaching pattern. The Train coaching from `failed-one-shot-triage/` includes spec decomposition; the size limit is the forcing function.

## What to do when a large PR is opened

The reviewer's response:

1. **Read the size flag**
2. **Ask: should this be split?** If yes, request the split before reviewing the diff.
3. **If genuinely atomic**: the bypass label is added; reviewer proceeds knowing the size is justified.
4. **If splittable but large**: don't review the whole thing. Request split first.

This is the discipline. If reviewers review large PRs anyway, the limit is decorative.

## What good size discipline looks like

Healthy:
- Average PR size: 100-250 lines
- Median PR size: 50-150 lines
- 90th percentile PR size: 300-400 lines
- Large PR rate (>400 lines): <10% of PRs

Concerning:
- Average PR size: 300+ lines
- Median: 200+ lines
- Large PR rate: >25% of PRs

If size is climbing, the discipline is eroding. Investigate.

## Anti-patterns

### Limit without enforcement

The limit exists; nobody flags PRs that exceed. Decorative.

Mitigation: CI check is the mechanical enforcement. Without it, the discipline relies on memory.

### Bypass too easy

Engineers add the bypass label routinely. Limit becomes performative.

Mitigation: track bypass rate. If >20% of large PRs use bypass, the discipline is broken.

### Limit too tight

The limit is 200 lines; most legitimate work exceeds. Engineers spend time gaming the system.

Mitigation: calibrate the limit. 400 lines is the recommended; adjust based on team's actual work patterns.

### Limit applied uniformly

Migration PRs and feature PRs have the same limit. Migrations need to be atomic.

Mitigation: path-specific limits or explicit bypass for known-atomic patterns.

### Reviewers review large PRs anyway

A 700-line PR is opened; reviewer reads the whole thing. The limit is theoretical.

Mitigation: reviewers reject (politely) and request split. The 60-second comment "please split this" is the discipline.

## Cost of the limit

The limit has costs:
- More PRs (decomposition produces more, smaller PRs)
- More overhead per PR (CI runs per PR; review per PR)
- Some friction (engineers feel slower)

The benefits exceed the costs in most teams:
- Lower review fatigue
- Better issue detection
- Faster median time-to-merge (smaller PRs review faster individually)
- Lower revert rate
